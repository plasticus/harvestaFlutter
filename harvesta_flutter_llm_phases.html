BEFORE YOU START

How to Work With an LLM on This Project

🎯 The PHP Files Are Your Context

Your existing PHP files are the best context you can give an LLM. For each phase, paste the relevant PHP file(s) directly into the prompt. The LLM reads the logic and translates it — you don't need to describe systems in natural language when the code is already there.

🧩 One System Per Session

Never ask the LLM to "port the whole game." Break it into systems that match these phases. A scoped task ("implement the market pricing system in Dart, here's the PHP reference") produces clean, verifiable output. Vague tasks produce a mess.

✅ LLMs Are Great At…

  • Generating Drift table schemas from SQL
  • Writing Riverpod providers with clear specs
  • Translating pure math/logic (formulas, dice rolls)
  • Building Flutter widget trees from descriptions
  • Writing freezed/json_serializable boilerplate
  • Seeding static data (ship catalog, modules) as Dart maps

🚫 LLMs Struggle With…

  • Holding the full game state in mind across many sessions
  • Subtle game balance bugs (always verify the math)
  • Complex Flutter animation sequences without a clear spec
  • Database migrations (always review generated migration code)
  • Catching logical contradictions across multiple files

⚠️ Always Run the Gate Checklist

Before moving to the next phase, run every item on that phase's deliverables checklist. Don't let the LLM move forward if the previous system has untested logic — bugs compound fast when systems depend on each other.

⚠️ Maintain a CONTEXT.md File

Keep a living CONTEXT.md in the Flutter project root that the LLM reads at the start of every session: architecture decisions, naming conventions, which providers exist, which tables exist, completed phases. This is the LLM's memory across sessions.

Contextual Trigger Conditions

Gregg checks game state each turn and picks the most relevant advice category:

● Good Net Worth Growth — compliments your recent turn performance

Implementation note for the LLM (Phase 10): Build a GreggAdvisorService in lib/game/advisor/ that takes a GameStateSnapshot (turn, Solars, net worth delta, leaderboard position, damaged ships, recent research level-up, skipped mission flag) and returns a GreggAdvice object containing 2–3 lines of text. Lines are selected from condition-keyed string pools with light randomization so Gregg doesn't repeat himself verbatim every turn. Render on the Corp HQ screen as a small dismissible card with Gregg's name. Keep all string data in lib/config/gregg_lines.dart so it's easy to expand later and to swap out when additional advisors are added.

Database Schema & Seed Data

1.5–2 weeksData Foundation

What the LLM Builds

  • All Drift @DataClassName table definitions, one per PHP table

  • DAO classes per logical domain: FleetDao, CrewDao, InventoryDao, MissionDao, etc.

Feed the LLM These Files

udgdwxxz_harvesta(2).sql data.php db.php

Paste the CREATE TABLE statements from the SQL dump. Also paste data.php — it contains all ship model stats, module definitions, and commodity names as PHP arrays that the LLM can convert to Dart seed data maps.

Sample Prompt

Here is the SQL schema for the harVesta database. Convert each CREATE TABLE into a Drift table class. Produce: 1. One Dart file per table in lib/data/tables/ 2. A central AppDatabase in lib/data/app_database.dart 3. Use int primary keys where SQL uses INT AUTO_INCREMENT 4. TextColumn for VARCHAR, IntColumn for INT, RealColumn for DECIMAL/FLOAT [paste SQL CREATE TABLE statements here]

Gate Checklist

  • dart run build_runner build completes with no errors
  • App launches and creates SQLite DB on first run
  • Seeder populates ship models, modules, asteroids on fresh install
  • GameDataDao.getTurn() returns turn 1
  • All 27 tables visible in DB Inspector

Watch Out For

  • The combatTable scratch table is a PHP global state hack. In Flutter it becomes a Riverpod StateProvider<CombatState?> — not a DB table. Have the LLM skip it here and note it for Phase 7.
  • Dynamic tables (corp_turn_actions, corpFinanceLedger) — implement them as proper Drift tables; don't replicate the "CREATE IF NOT EXISTS on first access" pattern.

3
Economy: Market, Resources & Financial Ledger
7-commodity market, deterministic pricing, corp inventory, P&L ledger, fl_chart analytics
1–1.5 weeksMoney Systems

What the LLM Builds

  • MarketPriceService — pure Dart, no DB. Deterministic formula: hash(commodityName + gameTurn) → ±10% variance. Buy = base × 1.20 × tradeBonus; Sell = base × 0.90 × tradeBonus.
  • InventoryProvider — corp's current Solars + 7 commodity quantities from DB
  • MarketScreen — buy/sell UI per commodity with live price, quantity slider, confirm
  • LedgerService — records per-turn P&L snapshots to CorpFinanceLedger table on turn advance
  • LedgerScreen — fl_chart line chart for net worth trajectory + revenue/expense breakdown table

Feed the LLM These Files

market.php market-trade.php ledger.class.php ledger.php

The pricing formula is self-contained in market.php. PHP's crc32() can return negative integers — Dart doesn't have a built-in crc32. Ask the LLM to use a simple consistent hash (fnv1a or similar). Only turn-to-turn consistency matters, not matching the PHP values exactly.

Gate Checklist

  • Market prices vary turn-to-turn deterministically (same turn = same price on repeat)
  • Buy/sell transactions correctly update Solars and commodity quantities
  • Trade Relationships research bonus (3%/level, max 20%) applies at the service level
  • Ledger records a P&L row on each turn advance
  • Net worth chart renders correctly in fl_chart over multiple turns

Watch Out For

  • Solars balance exists in corpInventory and is reflected in net worth — make sure they're sourced from the same DB row, never duplicated.
  • Research bonuses are cross-cutting — verify the Trade Relationships bonus is applied in MarketPriceService, not just described somewhere.

Mission Board, Runner & Interruptors
Mission generation, 3-waypoint cockpit state machine, all 10 sector encounter scenarios
2.5–4 weeksMost Interesting Phase

What the LLM Builds

  • MissionGeneratorService — 5 missions per turn, 9 types, templated narrative, distance 0.20–6.00 AU, fuel cost deduction (⁂1,200/AU)
  • MissionBoardScreen — view available missions with type/distance/payout/bonus
  • MissionStateProvider (Riverpod StateNotifier) — the 3-waypoint state machine: SquadronSelect → Waypoint1 → Interruptor? → Waypoint2 → Interruptor? → Waypoint3 → Outcome
  • MissionCockpitScreen — waypoint cockpit UI with narrative text and squadron status
  • InterruptorEngine — sealed class hierarchy (one subclass per encounter type). Each resolve(SquadronSnapshot, int threatRating) rolls dice against squadron stats, returns InterruptorOutcome
  • 10 interruptor scenario widgets with choice buttons and outcome display

Feed the LLM These Files

mission.php mission-generate.php mission-zonulae.php mission-confirm.php interruptors.class.php mission_narrative.class.php

The interruptors file (915 lines) is the richest context. Feed it with the explicit instruction below — the key is removing global PHP dependencies.

Key Interruptors Prompt

interruptors.class.php uses global PHP variables ($link, $_SESSION, $crew, $squadron, $CR). Replace ALL global dependencies with explicit Dart constructor parameters: - SquadronSnapshot (immutable stats snapshot) - int threatRating (replaces $CR) Do NOT use global state. Each interruptor resolves purely from its input parameters. Use a sealed class hierarchy — one subclass per encounter type. Not a switch statement.

Gate Checklist

  • 5 missions generate correctly on turn advance
  • Fuel cost deducted from payout based on mission distance
  • Mission runner progresses through all 3 waypoints
  • Interruptors fire at correct waypoints and present choices
  • All 10 encounter types tested; dice rolls produce correct probability spread
  • Mission outcomes (payout, bonus, resources) correctly update DB
  • Mid-mission state persists to DB so it survives app restarts

Watch Out For

  • The LLM will often default to a giant switch statement for the interruptors. Insist on sealed classes — far more maintainable and easier to extend later.
  • PHP session-based mission state doesn't survive app close. Design the Riverpod state provider to persist mid-mission state to DB so it survives restarts.

Combat Engine — Pure Dart Logic
Port the PHP Naval Combat Engine v2 math to pure Dart — no UI yet, just the engine and unit tests
2–3 weeksHardest Logic

What the LLM Builds (Logic Only — No Flutter Imports)

  • CombatEngine class in lib/game/combat/
  • Input: immutable PlayerSquadron + EnemySquadron snapshots taken from DB before combat
  • Output: CombatLog — list of CombatRound objects with full state per round
  • 6-subsystem degradation per ship (Engines, Weapons, Maneuv, LifeSupp, Cargo, Hull)
  • Weapon initiative ordering (WeapCtrl stat)
  • Crew skill modifiers: Captain → morale, FO → attack, Pilot → defense, SO → in-combat repair
  • Ship quirk penalties applied at combat start
  • Morale cascade logic
  • Surrender condition checking
  • After-Action Report (AAR) generation: damage totals, casualties, XP awards, payout, net profit
  • Dart unit test file covering all the above

Feed the LLM These Files

battle_v2.class.php battle.class.php

battle_v2.class.php is 1,222 lines. Feed it in chunks if context is limited: first class properties + constructor, then the main battle loop, then the AAR calculation. Have the LLM build the unit test harness alongside, not after.

Key Combat Engine Prompt

Port this PHP combat engine to pure Dart. No Flutter imports. No database calls inside the engine — all data passed in as immutable snapshot objects at construction time. The engine must be deterministic given the same inputs and the same Random seed. Add a seed parameter to support replays and testing. Output a CombatLog with a List of CombatRound objects (one per exchange). Each round must record enough state to animate the combat later — do not discard intermediate subsystem values.

Gate Checklist

  • Unit test: 100 combats run without null exceptions or infinite loops
  • All ships eventually reach 0 HP or combat ends by round cap
  • AAR payout is always non-negative
  • Determinism test: same seed + same inputs = identical CombatLog
  • Crew skill modifiers visibly change outcomes (test maxed vs baseline crew)
  • Ship quirks apply subsystem penalties in round 1 state
  • Zero Flutter or DB imports anywhere in lib/game/combat/

Watch Out For

  • The PHP engine uses a global combatTable scratch table — ensure the LLM does NOT replicate this. All state is in-memory in Dart.
  • The LLM may simplify morale cascades or quirk penalties. Cross-check the PHP formulas explicitly and verify they match in test output.
  • Dart's Random requires explicit seeding for reproducibility — make sure the LLM wires this up from the start, not as an afterthought.

Combat Screen Prompt

The CombatEngine (lib/game/combat/) produces a CombatLog. Build a Flutter CombatScreen that: 1. Takes a CombatLog as input (pre-computed) 2. Plays through rounds using a Timer 3. Left column: player ships. Right: enemy ships. 4. Each ship: name + 6 LinearProgressIndicator bars for Hull, Engines, WeapCtrl, Maneuv, LifeSupp, Cargo 5. The screen does NOT re-run the engine — it only reads from the pre-computed CombatLog.

Gate Checklist

  • Combat plays through all rounds without errors or skips
  • All 6 subsystem bars update correctly each round
  • Destroyed ships visually indicate destruction (greyed out)
  • Instant mode jumps to final state and shows AAR immediately

Watch Out For

  • Start simple: step through CombatRounds with a fixed-interval Timer. Add flutter_animate polish after the logic is verified — not before.
  • The combat screen must NOT re-run the CombatEngine during playback. The log is pre-computed. Playback only reads from it.
