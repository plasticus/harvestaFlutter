harVesta → Android
Port Analysis

Assessment of scope, effort, and approach for migrating the harVesta multiplayer web game to a single-player Android application.

📅 August 2026 🌐 Source: PHP 8.4 + MariaDB 📱 Target: Android (Kotlin / Jetpack Compose) 🎮 Genre: Turn-based Corp Strategy
7 / 10Portability
⬡ TL;DR Verdict

Definitely doable — but it's a significant rewrite, not a port.

The good news: harVesta's gameplay loop is naturally single-player. The "multiplayer" is almost entirely a cosmetic shared leaderboard — the core game systems (mining, research, fleet, missions, combat) are per-corp and fully independent. Almost everything that actually matters to the player experience ports cleanly to a single-device Android game. The bad news: the entire tech stack is non-transferable. Raw PHP/MySQL has no path to Android. Every system will need to be rebuilt in Kotlin, with SQLite (Room) replacing the database, and every server-side render replaced with proper Android UI. There is no "easy" path here, but there is a very clear path, and the game design itself is a genuine asset — it's a solid, well-thought-out game.

01

What You're Actually Porting

🎮 The Game

harVesta is a turn-based space corporate management and strategy game set in The Asteroid Belt. Players run a mining corporation — scanning asteroids, dispatching fleets, running missions, conducting research, training officers, and managing a ship fleet — all competing against AI rivals on a shared leaderboard.

🔁 Core Loop Per Turn

  • Radar sweep → scan asteroids
  • Dispatch squadron → mine/salvage
  • Accept & run a mission contract
  • Progress research in a chosen discipline
  • Train cadets at the academy
  • Trade resources at the market
  • Advance the turn (AI corps take their moves)

⚔️ Combat

Full broadside naval-style combat with 6 subsystems per ship (Engines, Weapons, Maneuverability, Life Support, Cargo, Hull). Crew skills, ship quirks/personalities, morale cascades, tactical directives, and animated playback.

👥 "Multiplayer" Reality Check

The multiplayer element is a shared leaderboard and fleet directory. All actual gameplay — every action, every mission, every combat — is entirely isolated per player. Six AI corporations simulate competition. There is no direct player-vs-player, no trading between players, no messaging, no alliances. This is already essentially a single-player game.

04

What Works In Your Favor

✅ The Gameplay Is Already Single-Player

The shared leaderboard is the only genuinely multi-user feature. Every combat, mission, mining run, and research push is 100% isolated per player. You lose almost nothing meaningful by dropping the "multiplayer" label.

✅ No Networking Architecture to Untangle

There's no WebSocket server, no real-time sync, no message queue. The web server is just a database host. Replacing it with a local SQLite database is a clean, well-understood trade.

✅ Data-Driven Design Throughout

The ship catalog (38 models), module catalog (26 modules), 10 research disciplines, 7 commodities, asteroid list (~400 entries), and mission narrative templates are all table-driven. They migrate cleanly to JSON bundles or seeded Room databases — no logic needs to change.

✅ The Turn System Is Trivially Simple

A single integer in a database table. "Advance Turn" is a function call. No server clock, no concurrency, no race conditions. Perfect for a local game loop.

✅ Market Pricing Is Deterministic & Serverless

Commodity prices use crc32(name) + gameTurn — a pure math formula. Already cheat-resistant and server-independent. Works identically offline on Android.

✅ The Aesthetic Translates to Android Beautifully

The glassmorphic dark theme, neon cyan/amber palette, monospace HUD fonts, and CRT telemetry aesthetic are all at home on a dark-mode Android app. Material3 dynamic theming with custom color schemes can replicate this exactly.

✅ Fully Offline Game

No always-on server required. The game needs no internet connection to function. This means no backend maintenance cost, no server hosting fees, no latency concerns — just a local app.

✅ The Schema Is Your Blueprint

The 867KB SQL dump is a detailed, tested game state specification. Every Room @Entity class can be derived directly from it. You already know exactly what data the game needs — that's not a question you'll need to answer during development.

05

The Hard Parts

🚫 Zero Code Reuse

PHP ≠ Kotlin. Not a line of existing code can be compiled or run on Android. Every class, every query, every function must be rebuilt. The existing codebase is a reference implementation, not a starting point.

🚫 Combat Animation Engine — Full Rebuild

The combat engine outputs a JSON blob that a custom JavaScript renderer animates in the browser. On Android, this becomes a Jetpack Compose Canvas animation system or a LibGDX scene graph — a completely different rendering paradigm requiring significant original work.

🚫 15+ Major Screens to Design & Build

Corp HQ, Station, Fleet, Shipyard, Mission Board, Mission Cockpit (3-waypoint), Interruptor encounters, Combat screen, Market, Ledger/Charts, Cadet Academy, Research Lab, Codex, Officer profiles... Each is a non-trivial Compose screen with its own state management.

🚫 PHP Session State → Android State Machine

The 3-waypoint mission runner uses PHP $_SESSION to persist state across HTTP requests. On Android, this becomes a ViewModel-backed state machine with persistent Room storage — a conceptual simplification, but requires careful architecture planning upfront.

⚠️ Interruptors Are Deeply Coupled to Globals

The interruptor system references global $link, $_SESSION, $crew, $squadron, $CR, $numShips. The logic is portable but needs to be refactored into a clean dependency-injected system before it can be ported. Consider this a refactor, not a direct translation.

⚠️ AI Corp Engine Needs All Subsystems First

The AI runs scan, mine, research, build, and purchase actions. This means it touches almost every game system. The AI can only be built after the core systems are complete — it cannot be developed independently early on.

⚠️ No Existing Android Expertise Required but Implied

Kotlin + Jetpack Compose + Room + ViewModel/StateFlow is a modern, coherent Android stack — but it has a real learning curve if the team primarily works in PHP. The paradigm shift (reactive UI, coroutines, dependency injection) is significant.

⚠️ Save File Management

The web version has no concept of "save slots" — one account, one state. An Android game needs save slot management, potentially cloud save (Google Play Games), and backup/restore. These are new features with no web equivalent to reference.

06

Three Possible Approaches

🌐 Option A — Hybrid WebView

Wrap the existing PHP web game in an Android WebView, pointing to the hosted server.

Fastest to "ship" an Android app
Zero gameplay logic rewrite
Requires a live server — not truly a local app
PHP session handling in WebView is fragile
Not single-player / offline — server still required
Terrible UX on mobile (tiny PHP HTML is not touch-friendly)
Play Store submission risk (Google disfavors WebView-only apps)
Doesn't solve the "single-player" goal at all
⛔ Not Recommended
📱 Option B — Native Android Port

Full rewrite in Kotlin + Jetpack Compose + Room. The web game serves as a design spec and reference implementation.

Fully offline / single-player — no server dependency
Native performance and Android UX conventions
Play Store compliant — no WebView restrictions
Maintainable, modern codebase
The game design is already solid and validated
Largest upfront effort — 6–12 months solo developer
Zero code reuse from existing PHP
Requires Android/Kotlin expertise
✅ Recommended
🎮 Option C — Game Engine (Unity/Godot)

Port to Unity (C#) or Godot (GDScript/C#) targeting Android, using the web game as the design document.

Built-in animation/rendering for combat sequences
Cross-platform (Android + iOS + PC) from one codebase
Rich asset pipeline for UI transitions and effects
Largest paradigm shift from PHP — new engine, new language
Turn-based strategy games don't need a real-time engine
Unity licensing overhead (cost, terms)
Overkill for a UI-heavy turn-based game
🤔 Consider If Cross-Platform Is a Goal

08

What Gets Dropped or Changed

🗑️ Shared Leaderboard

No longer a live cross-player board. Replaced with a local "Intel" screen showing your corp vs the AI corps only. Or optionally, a cloud leaderboard via Google Play Games Services.

🗑️ Email Verification / Account System

No user accounts needed. The game runs locally. Save slots managed by the app. No SMTP, no bcrypt password hashing, no login screen.

🗑️ Admin Console

The login/admin.php turn-advancement and moderation panel has no equivalent in a single-player app. Debug menus can replace it during development.

🗑️ Shared Fleet / Officer Directory

Currently visible to all players. In single-player, the equivalent is an "Intel" screen showing AI corp fleet data (for competitive context). Same data, different framing.

✨ Gains: Save Slots

A web game has one persistent state per account. A single-player Android game gets multiple named save slots — a meaningful quality-of-life upgrade.

✨ Gains: Offline Play

Zero internet required. Play on a plane, on the subway, anywhere. The web version requires a server connection and isn't feasible offline.

✨ Gains: Push Notifications

Android enables notifications like "Your research is complete," "New mission contracts available," or "Your ships are repaired" — enhancing engagement in ways a web game cannot.

✨ Gains: Touch-Native UI

The current UI is desktop-first (collapsible sidebar, small form inputs, dense tables). A rebuilt Compose UI can be designed touch-first with proper gesture support, larger tap targets, and adaptive layouts.

✨ Gains: Haptic Feedback

Combat hits, mission outcomes, and level-up events can trigger haptic patterns — something impossible in a browser game.

09

Is This Starting From Scratch?

🔴 Technically: Yes

From a code standpoint, you are starting from scratch. Zero PHP files transfer to Android. The entire tech stack — language, framework, database driver, rendering layer — is different. No toolchain is shared.

🟢 Conceptually: Absolutely Not

  • The game design is done and proven
  • The data models are fully specified (27-table schema)
  • The game balance has been tuned (ship values, mission payouts, market prices, research curves)
  • The content exists: 38 ship models, 26 modules, 10 research disciplines, 400 asteroids, 10 interruptor scenarios, 9 mission types
  • The combat engine logic is documented in 1,200 lines of readable PHP — a complete reference implementation to port from
  • The AI behavior is specified and tested
  • The art direction (glassmorphic dark, neon cyan/amber) is established
The honest answer: You are not starting the game from scratch. You are starting the codebase from scratch. The web version serves as a complete, playable design spec. Every design decision has already been made and validated. You won't be asking "how should combat work?" or "how many ship models should there be?" — those answers are already in the PHP files. That's a massive head start compared to a ground-up greenfield project.
